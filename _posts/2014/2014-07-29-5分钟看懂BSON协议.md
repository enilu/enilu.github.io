BSON 是一种带类型信息的二进制文档格式。理解它最直接的方法，是从一个小文档开始，逐字节对应长度、字段名和字段值，而不是把它当成“压缩后的 JSON 字符串”。

## 从一个整数开始

以下文档将 a 保存为 BSON int32：

```json
{"a": 1}
```

它的 BSON 字节可以写成：

```text
0c 00 00 00  10  61 00  01 00 00 00  00
```

| 字节 | 含义 |
|---|---|
| `0c 00 00 00` | 文档总长度 12 字节，包含长度字段自身和结尾 0 |
| `10` | 元素类型 int32，十六进制 0x10 |
| `61 00` | UTF-8 字段名 a，使用 0 结尾的 cstring |
| `01 00 00 00` | 整数 1，采用 little-endian |
| `00` | 文档结束标记 |

总长度为 4 + 1 + 2 + 4 + 1 = 12。换成 int64，即使数值仍是 1，元素类型与值的字节数也会变化。

## 字符串长度是字节数

对于 `{"name":"张三"}`，BSON string 值需要一个 int32 长度、UTF-8 内容和结尾 0。张、三各占 3 个 UTF-8 字节，因此值的长度字段为 7，包含字符串结尾的 0。

完整文档长度是 4 + 1 + 5 + 4 + 7 + 1 = 22 字节，其中 name 的字段名占 5 字节，已经包含自己的结尾 0。

## 文档、字符串和 binary 是不同类型

把 `{"id":1}` 作为字符串保存，不会自动变成嵌套文档。若希望其中字段可被按结构理解，应编码为 BSON document；若保存原始字节，则是 binary 类型，还需要长度和 subtype。

因此看到类型字节 0x05 时，后面的数据首先应该按 binary 解释，不能仅凭字节看起来像文本就认定它是 BSON string。字符采用 UTF-8 还是其他编码，也由真实编码过程决定，不能从 Java 字符串的概念推测。

BSON 保留字段名、类型与长度，不保证比对应 JSON 文本更小。它的价值在于明确的数据类型和可解析的结构。实现解析器时，还需要检查长度边界、结尾标记和未知类型，而不能信任输入声明的长度。

参考：[BSON 规范](https://bsonspec.org/spec.html)。
